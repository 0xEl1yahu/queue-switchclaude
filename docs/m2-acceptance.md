# M2 live acceptance

Run on 2026-10-19 (12:05 to 12:15 UTC, 13:05 to 13:15 BST) in Claude Code 2.1.302 with Opus 5.5, auto permission mode, plugin loaded with `--plugin-dir` from the main checkout at commit `c0d9680` (data dir `~/.claude/plugins/data/queue-switchclaude-inline/`). Same method as `docs/m1-acceptance.md`: the session ran in tmux (150x45) in `/tmp/qsc-demo`, a scratch `git init` repo with no files. Messages were typed with `tmux send-keys -l` and sent with `Enter`; each send was timestamped in UTC (perl `Time::HiRes`, taken just before the `Enter`) so hook delay could be read against the `ts` of the matching log line. Mid-run messages were sent 2.4 s after the first prompt of the scenario (2.0 s of spacing plus the typing time); the pane was captured 1.5 s after each send and again once the turn ended (polled every 3 s). Each scenario began with `/clear`, which gives a new session id and therefore a fresh store, log, `plans/` and `handoffs/`. The input box was cleared with Ctrl-U before each message because a blocked message returns to it (M1 issue 6); the one time this was not done (before O's `/clear`) is recorded under O.

Delay means the time from pressing Enter to the intake hook writing its log line. Three send timestamps (K's `lgtm`, L's revise message, and K's first prompt) were lost to output trimming in the operator's capture script; those delays are given from the log line and the classifier's own `latency_ms`, and are marked approximate.

Scenarios K to O of the M2 plan (`docs/superpowers/plans/2026-10-19-m2-plan-flow.md`, Task 9). No scenario was run twice. No plugin code was changed; 492 tests passed before the run.

## Issues found

1. **Messages wait for the store lock while the Stop hook judges.** In M the rules-only `queue: verify p2` took 3.95 s instead of the usual 60 to 120 ms because dispatch held the lock through the `claude -p` judge call (about 4 to 7 s per Stop in this run). Any message typed in the seconds after Claude's closing message pays this; the hook status line shows the wait. The order was still correct (the verify was recorded before the plan was written). Either judge outside the lock, or accept and document the latency.
2. **Auto tasks get two handovers for one execution** (N). The planning handover already says `carry it out immediately without waiting`, so Claude plans and executes in the planning turn; stage B then finds the plan file and issues `task p2 is approved. Execute the plan …` anyway, which costs an extra model continuation and reads oddly (`approved` for a task that never waited). Either drop the `carry it out` clause so the planning turn only plans and stage B drives execution, or have stage B recognise an auto task whose planning turn already finished (judge the closing message there) and skip the execution handover.
3. **Nothing on screen marks `gave_up`** (M). After the second handback the task is closed with `verdict: gave_up` in the log and the handoff, but the user sees only Claude's own `I'm stopping here` message; the harness does not say that it stopped retrying or that `p3` is now `done`. A `systemMessage` or a final handback line (`queue-switchclaude: gave up on p3 after 2 verify failures; it is marked done`) would make the state visible. Related cosmetic point: the handback prints `Output tail: .` when the command produced no output.
4. **An unrelated question while waiting costs three model calls** (O): the classifier (4.0 s) to route it, the judge to close it as a task (`p5`, with a handoff file), and the re-present continuation. Behaviour matches review focus 1 exactly and the plan is never lost, but a plain question becomes a task record with its own `handoffs/p5.md`. If questions should not become tasks, intake would need to tell a question from a new task before `new_turn`.
5. **Held text in the input box bit the operator** (O). The known M1 issue 6 (a blocked message returns to the input box) turned `/clear` into `queue: auto p2/clear`, blocked with `no task p2/clear`. The control rule's reply made the mistake obvious, but a leading `/` command appended to held text is an easy slip after any `queue:` message.
6. **Not covered by this run.** The `awaiting_answer` state (Claude asks a question during a task; `decision: answer` / `confirm`) never arose, since every task closed `done`. The `queue: approve`, `manual` and `show` control commands were not typed; `approve` as a bare word was matched by `rules.is_approval` instead. The mid-run `queued pN` notification was seen on screen in K only; in L to O the 1.5 s captures did not include it while the diff side panel was open (M1 issue 3), although the log shows every block.
